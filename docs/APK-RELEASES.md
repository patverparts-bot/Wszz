# Обновление Android-приложения через админку

1. Войдите в админку под владельцем.
2. Откройте «Рабочий стол» (Աշխատանքային սեղան).
3. В блоке «Обновление Android-приложения» (Android հավելվածի թարմացում) выберите новый production APK. Описание изменений можно добавить по желанию.
4. Нажмите «Опубликовать новый APK» (Հրապարակել նոր APK-ը).
5. Дождитесь зелёного сообщения с номером опубликованной версии. Процент показывает передачу файла; после 100% сервер ещё проверяет APK.

Версия и внутренний номер версии читаются из APK автоматически. Сервер рассчитывает размер и SHA-256, загружает файл, проверяет сохранённое содержимое и только затем делает выпуск доступным в личном кабинете каталога и админке. Вручную изменять JSON, загружать файлы на GitHub и запускать команды не требуется. Чтобы увидеть обновление, достаточно заново открыть личный кабинет.

Новый APK должен относиться к приложению ZZWS (`am.zzws.admin`), быть production сборкой и иметь увеличенный Android versionCode. Максимальный размер — 50 МБ. Для установки поверх прежней версии сохраняйте прежний ключ подписи. Сервер проверяет структуру и метаданные APK; проверку Android-подписи выполняет устройство при установке.

Публикация доступна владельцу и использует обычное подтверждение пароля ZZWS. Скачивание нового файла разрешено только действующим аккаунтам с включённым разрешением APK. При ошибке загрузки предыдущий выпуск остаётся доступным. После успешной публикации автоматически сохраняются только две версии с наибольшим versionCode; более старые APK и их описания удаляются из Supabase Storage. Например, после публикации 7.0.11 останутся 7.0.10 и 7.0.11.

## Техническое сопровождение

Отдельная функция `zzws-apk` использует существующие отзываемые сеансы, действующий статус аккаунта, роли и настройки Android. Серверные ключи не передаются браузеру. Файлы хранятся в закрытом bucket `zzws-android-releases`: `files/<sha256>.apk`, `releases/<versionCode с ведущими нулями>.json`. Записи выпусков неизменяемые; актуальным считается наибольший versionCode. Сбой или одновременные загрузки не заменяют уже опубликованный файл и не понижают актуальную версию. Событие публикации записывается в журнал действий.

Пока через админку не опубликован первый APK, работает прежняя ссылка GitHub и `apk-release.json`. После первого выпуска серверное хранилище становится основным источником. Старые публичные APK с GitHub автоматически не удаляются.

Резервное копирование APK и метаданных в этом Storage bucket следует учитывать отдельно от резервной копии таблиц приложения. Скрипт `scripts/prepare-apk-release.mjs` сохранён для прежнего ручного способа публикации.

## Если загрузка прервалась

Пароль подтверждается до передачи большого файла. Затем отображаются процент и переданный объём, проверка на сервере и результат публикации. Передача и ожидание ответа ограничены двумя минутами; после обрыва интерфейс дополнительно проверяет текущий выпуск по SHA-256, размеру и описанию. Только точное совпадение считается успехом.

Если результат не подтверждён, форма снова доступна, выбранный файл и описание сохраняются. Проверьте строку текущей версии и повторите публикацию тем же APK и описанием. Повторная отправка уже опубликованного идентичного выпуска безопасна. При старом зависшем сообщении обновите страницу админки с Ctrl+F5 и выберите APK заново.

Транспорт публикации: `POST upload-check` перед передачей; `POST publish` с `application/octet-stream`. Тело: длина метаданных uint32 big-endian, UTF-8 JSON с filename/description, затем APK. Чтение тела ограничено размером и 90 секундами. Старая форма multipart возвращает просьбу обновить страницу.

Очистка запускается после полной проверки и публикации нового выпуска, а также при повторной отправке идентичного актуального APK. Используется Storage API; две актуальные версии защищены, незавершённые загрузки не удаляются. При временном сбое удаления публикация остаётся успешной, интерфейс сообщает об отложенной очистке; она повторяется при следующей публикации или повторной отправке того же файла. Старые публичные файлы GitHub и локальные сборки эта политика не затрагивает.
